The core idea

What surrounds a window

A window starts out knowing nothing. Then four different places each push something into it — rules, skills, tools, helpers. Every confusing thing here is one of two questions being mixed up.

2

Two questions, two different switches

Supply — does this thing exist in the window at all? Decided by where it lives and what scope it's switched on for.
Reach — is this particular window allowed to use it? Decided by the helper's own file. Keep them apart and everything else follows.

Four sources. Vendor terms first: user scope (~/.claude/) · the working directory and its parents · the agent file · the launch flags. here: floor · folder · file · flags

WHEN it enters

Five moments: launch · turn · dispatch · compaction · stop. A path-scoped rule is instructions (what), from the project folder (where), at the first matching read (when). One thing, three coordinates — the page When Things Arrive.

The seven direction rules — each mechanism has one home and reaches one way

1 · CLAUDE.md stacks upward. Open a deep folder and every CLAUDE.md above it loads too — user, then any folder above, then the project. Only the CLAUDE.md family stacks. measured
2 · Settings stay home. A folder's hooks, permission rules and plugin switches bind the launch folder only; a subfolder launch does not inherit them. "Project scope" means the folder you launched in. measured twice
3 · Agents climb to the repo root. Agent files are found walking up from the launch folder, but only as far as the git repository root. vendor doc
4 · Things below wake on touch. A nested CLAUDE.md, a nested skills folder, a path-scoped rule — none load at launch; they arrive when Claude reads a file down there. measured (rules)
5 · Auto memory follows the git repository. Every subfolder and worktree of one repo shares one memory directory; outside a repo, the folder itself. measured
6 · The agent's kit travels. Whatever an agent file carries — tools line, skills, hooks, its own memory — goes wherever that agent is launched or dispatched. measured (tools, hooks, skills)
7 · A CLAUDE.md can be pulled sideways, for one launch. --add-dir plus CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1 loads the added folder's CLAUDE.md and rules for that run only. vendor doc · untested here

These seven answer the folder-above-your-projects question in one line: a folder above contributes exactly one thing to the projects beneath it — its CLAUDE.md (rule 1). Its settings stay home (2), its agents are scanned only inside the same repo (3), and memory ignores it unless that folder is the git repository (5).

!
The one sentence: the folder decides what a window knows. The helper decides what it can do — and it decides it the same way however the helper arrives: from the machine floor (Layer 3, --agent name) or carried in by a plugin at launch (Layer 4, --plugin-dir … --agent plugin:name). And because rules and hooks both obey the folder, the helper file and the launch are the only two ways out of it.

Two verbs, one rule

Launch — the helper IS the window

claude --agent gap-checker. You talk to it. It gets the launch folder's rulebook, memory drawer and hooks, then its own file subtracts.

Dispatch — a window sends a child

The Agent tool, subagent_type: gap-checker. The child is born fresh and loads nothing of its own — it inherits the block the parent rendered at boot, then its own file subtracts.

!
Both verbs need the name on the roster of the seat doing the calling. A helper that exists on disk in some other project is not found from here — tested both ways. "Use the strategy-seat project's helper" from a monolith window really means "run this as the strategy-seat project": launch it there, and it brings the strategy seat's knowledge with it.

Hooks

Rules that run,
not rules that are read

The wall the index stands against

The documented limit: the first 200 lines OR 25 KB of the index — whichever comes first — load at start. Everything past that is silently dropped at load (the writer gets a warning; the reader gets nothing).

The direction rules — same tree, different answers

Rulebooks stack upward. Open a deep folder and every CLAUDE.md above it is added in.
Imports that leave the launch folder are gated, and headless runs decline them silently. Measured: an @ line pointing up or outside was ignored even as a full path, the line still visible. The vendor page names the mechanism: an import that resolves outside the working directory is "external" — an interactive window shows a one-time approval dialog; a headless run has nobody to answer it. User-scope files (~/.claude/CLAUDE.md) are trusted without the dialog, which is why constitution.md always arrives. Relative import paths resolve against the importing file, not the launch folder; up to four hops.
Rulebooks below you load lazily. A CLAUDE.md in a subfolder beneath the launch folder is not read at launch — it arrives when Claude reads a file in that subfolder (vendor docs). Same for a rule file with paths: frontmatter — tested today: absent at launch, injected on the first matching read.
Compaction treats them differently. The root CLAUDE.md and unscoped rules are re-injected from disk after a compaction; path-scoped rules and nested CLAUDE.md files are summarized away until a matching file is read again. The docs' own advice: if a rule must survive compaction, drop its paths: or move it to the root CLAUDE.md.
Memory follows the git repository. Every subfolder of one repo gets the repo's drawer (probed from strategy seat/reference/); a folder above the repo contributes nothing. Section 08.
Project settings don't flow down — tested twice today. A folder's plugin switch AND a folder's hooks both stop at the launch folder: a window in the subfolder reverted to the machine default, and the project hook fired for the parent launch but not the subfolder launch. "Project" means launch folder.
Folder rules stay home. Enforcement never follows work elsewhere — only rules carried by a helper, a plugin, or the launch travel.
A rulebook can be pulled sideways for one launch — opt-in (added 8/28). --add-dir gives a window another folder, but by default that folder's CLAUDE.md is not loaded. Set CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1 and the added folder's CLAUDE.md, .claude/CLAUDE.md, .claude/rules/*.md and CLAUDE.local.md load too (vendor doc; untested here). The seventh direction — lateral, per launch — and the only way to share a rules folder across repos without a symlink.

An eval grades the tool, never a piece of work — that is a different machine, and you already own it. This page is the whole eval side: what exists, what it costs, and what happened when a session stopped believing the question was closed. Measured 31 Aug – 1 Sep 2026, CLI 2.1.251.

Start here — two questions, one word

Verification — is this piece of work right?

Asked once, about one thing just produced. Answered by a judge at the exit, or by a fresh reader who did not do the work. You are fully built here: the seat Stop check is the judge, gap-checker is the fresh reader.

Evaluation — is this tool any good?

Asked about the tool itself, with fixed cases, run repeatedly. Answered by a score — or better, by the difference between two scores. Neither of your existing machines has an opinion about whether a skill is worth having.

That gap is what evals fill. Keeping the two apart is most of the topic.

Why a delta, not a score

Δ

A score alone cannot tell you the tool did anything

A skill that scores 8 out of 10 tells you nothing on its own, because you do not know what the same ten cases score with the skill switched off. If the answer is also 8, the skill is decoration. That is what the baseline arm is for — the same cases, run twice, once without. It is the write-vs-grade instinct pointed at a tool instead of a document.

!
The trap this session actually fell into. A test skill scored 3 out of 6 — and had fired zero times out of eighteen runs. Every point came from a "should not trigger" case passing, and they all passed for free: a skill that never fires never fires wrongly either. A dead skill scores 50% on a balanced set. ⇒ Read the fire count before you read the score.

Everything above this line was measured on a suite that had a bug in it. A later session built a suite from nothing — a skill, a case that should fire, a case that should not — and found that three graders out of three were faulty, each in a different way. None of them announced it. Each one reported a number. The four settings below are the difference between a suite that measures something and a suite that reports confidently on nothing.

How much the number wobbles — measured on purpose, and it is worse than it looks

The page above retires +0.17 because of this measurement. Here is the measurement itself: three identical batches — same case, same graders, same settings, nothing changed between them — scored +0.67 / +1.00 / +1.00. A spread of 0.33, a third of the whole scale, and the entire spread traces to two grader outcomes out of thirty-six.

⛔ Do not turn 0.33 into a threshold. Three points give a range that is a biased-low estimate of the real spread — three samples cannot find the edges. And with two graders across three runs, a score can only move in steps of 1/6 ≈ 0.167, so 0.33 is the second-smallest value this design can even express. A rule built on it was written and withdrawn the same day.
⭐ The rule that survived, and it needs no arithmetic: a delta that changes when you remove any one run is not a result. Drop each run in turn and look again. If the answer moves, you measured noise.
There are two layers of noise, not one. The model doing the work varies between runs — and the judge disagrees with itself on the same text: PASS FAIL PASS, FAIL PASS PASS, PASS PASS FAIL on identical answers. The three-vote majority absorbs the second layer. It is load-bearing, not decoration — a single judge vote is a coin with a bias you cannot see.
Where the money actually goes, and it is not where you would guess. Judge grading is $0.157 of $6.03 — 2.6% of the bill. The cost sits in the baseline arm: per successful run, with-tool $0.1075, without-tool $0.1918 — a ratio of 1.78×. Ordinary Claude works harder without the tool than with it. ⇒ The judge is not the thing to economise on, and switching off the baseline arm to save money removes the only part that makes the number mean anything. This is an addition to the $0.06 / $0.61 / ~$12 figures above, not a correction — those were measured two-arm and stand.
⛔ A failed run scores exactly like a bad answer. One run died on a transient sign-in error and reported score 0.00, judge FAIL FAIL FAIL, skill called 0× — indistinguishable from the tool being useless. Only a separate error line on the tool's own output told the two apart. ⚠️ Four exchanges went into theories about why before a plain retry worked with nothing changed. Check for an error line before you believe a zero.
Neither model was pinned in the runs behind this section — not the one doing the work (--model), not the one judging (--judge-model). Some of the wobble may be a model changing under the test. Pin both, or the run is not repeatable. Evidence: reference/claude-code/eval-authoring-measured-2026-09-02.md — 8 suite invocations, 45 runs, $6.03.

Walls

What stops an act —
as opposed to what asks

Instructions ask. Three mechanisms stop: a hook, a permission rule, and the sandbox. They sit in that order, each stronger than the last, and a fenced tools line sits in front of all three. here: sign on the door · doorman · locked door · wall

Permission rules — vendor terms

Three arrays in any settings file: allow, ask, deny. Each entry is a tool pattern: Bash(git *), Edit(src/**), Read(~/.env), WebFetch(domain:example.com), mcp__workspace-mcp__send_gmail_message. Precedence: deny > ask > allow — a deny anywhere blocks regardless. Lists merge across scopes (user + project + local + --settings); a single-valued setting does not.

.claude/settings.json — the grammar
"permissions": {
  "allow": [ "Bash(git status *)", "Read(**)" ],
  "ask":   [ "Bash(git push *)" ],
  "deny":  [ "Edit(~/Projects/knowledge-base/**)", "mcp__workspace-mcp__send_gmail_message" ],
  "defaultMode": "acceptEdits"
}
Permission modes — the CLI's own list
default — shown as Manual in the mode indicator and in claude --help (the CLI also accepts manual): asks before anything not covered by a rule.
acceptEdits — file edits run without asking; commands still ask.
plan — reads and plans only; nothing is changed until you leave plan mode.
auto — everything runs, with a second model (a classifier) reviewing each action against your request instead of you; autoMode.environment is its policy (vendor doc).
dontAsk — never prompts: anything that would have asked is auto-denied; only what an allow rule, the built-in read-only Bash set, or a PreToolUse hook already approves runs. A locked-down mode, not a read-only one (vendor doc).
bypassPermissions — skips the prompts and the safety checks; a deny rule still blocks in every mode, including this one, and so do hooks and the sandbox. Allow rules stop mattering because nothing is asked (vendor doc). The floor's headless rings run under an enforced deny floor.

Set with --permission-mode <mode>, defaultMode in settings, or cycle live with Shift+Tab. Six modes; claude --help on this Mac (30 Aug, CLI 2.1.251) lists them as acceptEdits · auto · bypassPermissions · manual · dontAsk · plan — default and manual are the same mode. Definitions from the vendor's permission-modes page.

The sandbox — the strongest wall

The operating system itself fencing what a command may touch: which files, which network. Every Bash call and its children run inside it. sandbox.enabled: true in settings, or /sandbox to toggle; macOS, Linux, WSL. Off on this Mac. The vendor's own line: hooks are deterministic where CLAUDE.md is advisory; the sandbox lets the OS enforce which files and domains a command may touch.

Hooks as walls: several moments can refuse, each its own thing — only PreToolUse can stop a tool call before it runs (permissionDecision: deny); Stop refuses an exit; PreCompact refuses a compaction (the vendor's can-block table, and the binary carries the string). When several hooks match, the most restrictive answer wins — deny, defer, ask, allow. And a hook does not bypass the rules: deny and ask rules are evaluated whatever a PreToolUse hook returns, while a blocking hook beats an allow rule (vendor doc).

The order is real: the agent's tools line first (if the tool is not held, nothing else is consulted), then any PreToolUse hook, then the permission rules and mode, then the sandbox under every command.

      Why the moment matters more than the place

      Same place, two moments. Two rule files in the same .claude/rules/ folder: the one without paths: arrives at launch and is re-injected after a compaction; the one with paths: arrives mid-turn on a matching read and is summarized away at compaction. Measured.
      Dispatch is a copy, not a load. A subagent loads no instruction files of its own — it inherits the block its parent rendered at the parent's launch. A rule file written after the parent booted was invisible to a child dispatched a minute later. Only a fork copies the conversation too.
      Compaction is the one moment things die. Conversation-only instructions ("from now on, always…") do not survive it unless they were also written to a file the harness re-injects. The next page is about exactly that.
      Stop is where enforcement of the work lives. A Stop hook runs when the agent finishes responding, not on a user interrupt (vendor doc). The harness's own hook table reads "including clear, resume, compact" (a string in the binary), while the vendor names SessionEnd for exit, /clear and an interactive /resume, and SessionStart with a compact or resume source — so a check that must survive those is registered on those events too.       Compaction

      The window squeezes itself.
      What survives is decided by files.

      A window's context fills — every message, every file read, every tool result. When it nears the limit, Claude Code compacts: it folds the conversation into a summary and continues from that. Auto-compact is on by default and needs nobody present. The whole question is what comes back after the cut, and the answer is: whatever a file re-supplies.

      What a session is — four facts

      ONE CONVERSATION = ONE FILE
      Every session has a unique id and is appended to disk as you go: ~/.claude/projects/<encoded-folder>/<session-id>.jsonl. Plain JSONL — readable, greppable, yours. This window's file, 63aec6b8-….jsonl, was 10.4 MB / 5,818 records at 09:58 on 30 Aug and is larger by the time you read this — that is the point.
      FOLDER-SCOPED
      The folder you started in decides which directory here: drawer the file lands in (every / in the path becomes a -). claude --resume lists only that folder's sessions. There is no global inbox — which is exactly why old chats feel hard to find.

      Closing the terminal deletes nothing. Resume days later from the same folder, or from anywhere by id. A resume appends to the same file.
